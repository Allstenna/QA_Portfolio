# Протоколы HTTP и HTTPS
**Схема работы HTTPS-протокола**
**1. Инициация соединения**
Клиент (браузер) и сервер устанавливают базовое соединение
- **Цель**: Сообщить серверу о желании подключения к нему и инициировать соединение.
- **Устраняемый риск**: Несовместимость протоколов. При отсутствии единого способа шифрования данных стороны не смогли "договориться" о соединении, что сделало бы связь небезопасной (при отсутствии способа) или невозможной (различия в шифровании).

**2. SSL/TLS Рукопожатие (Handshake)**
Браузер отправляет запрос на защищенное соединение и список поддерживаемых алгоритмов шифрования, в ответ сервер присылает свой SSL/TLS-сертификат, содержащий публичный ключ. Далее браузер проверяет подлинность сертификата через удостоверяющий центр (CA), сверяет даты и доменное имя.
- **Цель**: Выбрать алгоритм шифрования и подтвердить подлинность сервера.
- **Устраняемый риск**: Без сертификата злоумышленник мог бы выдать себя за сервер. Сертификат гарантирует, что подключение происходит именно к оригиналу сайта, а не к фейковой копии.

**3. Обмен ключами (Асимметричное шифрование)**
Браузер генерирует случайный сеансовый ключ (симметричный), шифрует его публичным ключом сервера и отправляет его. Сервер, в свою очередь, расшифровывает сообщение своим приватным ключом, получая сеансовый ключ.
- **Цель**: Безопасно передать секретный материал для генерации сессионных ключей.
- **Устраняемый риск**: Так как сеанс зашифрован публичным ключом сервера, только сервер, владеющий приватным ключом, может его расшифровать. Даже если трафик перехватят, злоумышленник не получит ключи для расшифровки сессии.

**4. Защищенная передача данных (Симметричное шифрование)**
Браузер и сервер переходят на использование полученного симметричного ключа для шифрования всех последующих HTTP-запросов и ответов.
- **Цель**: Подтвердить целостность "рукопожатия" и начать обмен данными.
- **Устраняемый риск**: Подмена данных во время рукопожатия. Если бы злоумышленник изменил параметры на этапе 1-3, контрольные суммы в сообщении «Finished» не сошлись бы, и соединение было бы разорвано.

## Основные группы кодов состояния HTTP
|Код|Что видит пользователь|Что происходит на самом деле|Как тестировать|Куда эскалировать|
|-|-|-|-|-|
|100 (Continue)|Ничего (внутренний процесс)|Сервер получил заголовки и готов принять тело запроса|Отправить большой POST-запрос через curl/Postman с заголовком `Expect: 100-continue`|Backend (если сервер не отвечает 100 и сразу рвет соединение)|
|101 (Switching Protocols)|Ничего (смена протокола)|Сервер согласился сменить протокол (например, на WebSocket)|Попытаться установить WebSocket соединение (`Upgrade: websocket`)|Backend (если апгрейд не происходит)|
|200 (OK)|Страница загрузилась, данные сохранены|Запрос выполнен успешно, есть тело ответа|Проверить корректность данных в ответе (сверка с БД)|Frontend (если данные верны, но отображаются некорректно)|
|201 (Created)|Сообщение об успехе|Ресурс создан (обычно после POST), есть ссылка на новый объект|Создать новый объект (юзера, заказ), проверить ответ и наличие в БД|Backend (если объект не создался в БД, хотя код 201)|
|204 (No Content)|Ничего (страница не перезагрузилась, действие выполнено)|Успех, но тела ответа нет (часто при DELETE или обновлении)|Отправить DELETE запрос, убедиться, что ответ пустой, а ресурс удален|Backend (если пришло тело ответа или ресурс не удален)|
|301 (Moved Permanently)|Адрес в строке браузера изменился навсегда|Ресурс переехал навсегда. Браузер кэширует новый адрес|Запросить старый URL, проверить заголовок `Location` и кэширование|DevOps/Backend (настройка редиректов на сервере)|
|302 (Found (Temp))|Временная переадресация|Ресурс временно по другому адресу. Браузер не кэширует|Запросить URL, проверить, что при следующем запросе снова идет 302|Backend (логика временного редиректа)|
|304 (Not Modified)|Страница быстро загрузилась из кэша|Файл не менялся, сервер сказал брать из кэша браузера|Обновить страницу (F5), проверить заголовки `If-Modified-Since` / `ETag`|Frontend/DevOps (настройки кэширования)|
|400 (Bad Request)|"Некорректный запрос" или "Ошибка в форме"|Синтаксическая ошибка, валидация не прошла на уровне структуры|Отправить JSON с неверным типом данных или без обязательных полей|Frontend (если валидация не сработала на клиенте) или Backend (если сообщение об ошибке непонятное)|
|401 (Unauthorized)|"Войдите в систему" / "Сессия истекла"|Нет токена авторизации или он невалиден|Удалить куки/токен и попробовать доступ к личному кабинету|Backend (проблемы с генерацией/проверкой токенов)|
|403 (Forbidden)|"Доступ запрещен"|Авторизация есть, но нет прав на это действие (Role-Based Access)|Зайти под пользователем с ролью "User" и попробовать удалить админский ресурс|Backend (логика прав доступа)|
|404 (Not Found)|"Страница не найдена"|Ресурс с таким URL не существует|Ввести несуществующий ID в URL (`/users/999999`)|Frontend (битая ссылка) или Backend (если ресурс должен быть)|
|405 (Method Not Allowed)|"Метод не поддерживается"|Попытка сделать POST там, где только GET|Отправить POST запрос на эндпоинт, который принимает только GET|Backend (документация API или реализация метода)|
|500 (Internal Server Error)|"Что-то пошло не так" / "Ошибка на сайте"|Критическая ошибка в коде бэкенда (exception, null pointer)|Посмотреть логи сервера. Попробовать воспроизвести на тестовом окружении|Backend (баг в коде, логике, БД)|
|502 (Bad Gateway)|"Сервер временно недоступен"|Один сервер (балансировщик) получил неверный ответ от другого (апстрим)|Проверить статус сервисов (Nginx -> App Server). Перезагрузить сервис|DevOps (проблемы сети, конфиги прокси, упавший сервис)|
|503 (Service Unavailable)|"Технические работы" / "Сервер перегружен"|Сервер жив, но временно не обрабатывает запросы (лимиты, режим обслуживания)|Нагрузочное тестирование (превышение лимита соединений)|DevOps/Backend (масштабирование, лимиты rate-limiting)|
|504 (Gateway Timeout)|"Время ожидания истекло"|Сервер-посредник не дождался ответа от основного сервера|Имитировать долгий запрос (sleep в коде БД) или отключить БД|Backend (медленные запросы) или DevOps (таймауты прокси)|
